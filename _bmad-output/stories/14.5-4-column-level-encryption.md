# Story 14.5-4: Column-Level Encryption

Status: Ready for Dev
Priority: P0

## Dependencies

- **Story 14.5-2** (Privacy Consent Dialog): Encryption should only apply to users who have consented to data storage
- **Epic 15** (`prompt_responses` table): This story initially implements encryption for the `prompts` table. When Epic 15 adds the `prompt_responses` table, encryption should be extended to that table using the same pattern established here.

## Story

**As a** system administrator,
**I want** sensitive data columns encrypted at rest,
**So that** even database breaches do not expose raw prompt or response content.

## Acceptance Criteria

1. **Given** Supabase pgcrypto extension
   **When** the system initializes
   **Then** the extension is enabled and encryption functions are available

2. **Given** a new prompt is captured
   **When** it is stored in the database
   **Then** the `text` column is encrypted using pgcrypto
   **And** the encryption key version is recorded

3. **Given** a response is captured
   **When** it is stored in the database
   **Then** the `response_text` column is encrypted

4. **Given** an application needs to read prompt text
   **When** it queries the database
   **Then** the text is decrypted transparently via database function

5. **Given** the encryption key needs rotation
   **When** an admin initiates key rotation
   **Then** a new key version is created
   **And** old data can still be decrypted with the old key
   **And** new data uses the new key

6. **Given** a key rotation is in progress
   **When** the system runs the re-encryption job
   **Then** old records are re-encrypted with the new key
   **And** the job can be paused and resumed

7. **Given** audit requirements
   **When** encryption operations occur
   **Then** key version usage is logged
   **And** no plaintext is written to logs

8. **Given** encryption/decryption operations
   **When** measuring performance
   **Then** each read or write operation completes in <50ms
   **And** batch operations of 100 records complete in <5 seconds

9. **Given** existing unencrypted prompt data
   **When** the migration is applied
   **Then** a backfill job encrypts all existing plaintext data
   **And** the backfill runs in batches to avoid database locks
   **And** progress is tracked and resumable

### Database Schema

```sql
-- Migration: 20251223000001_column_level_encryption.sql

-- 1. Ensure pgcrypto is enabled
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 2. Create encryption key tracking table
CREATE TABLE encryption_keys (
  id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
  key_version INTEGER NOT NULL UNIQUE,
  created_at TIMESTAMPTZ DEFAULT NOW(),
  rotated_at TIMESTAMPTZ,
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'rotating', 'retired')),
  vault_secret_name TEXT NOT NULL
);

-- Insert initial key version
INSERT INTO encryption_keys (key_version, vault_secret_name, status)
VALUES (1, 'contextor_encryption_key_v1', 'active');

-- 3. Create helper function to get active key
CREATE OR REPLACE FUNCTION get_active_encryption_key()
RETURNS TEXT AS $$
DECLARE
  key_name TEXT;
  key_value TEXT;
BEGIN
  SELECT vault_secret_name INTO key_name
  FROM encryption_keys
  WHERE status = 'active'
  ORDER BY key_version DESC
  LIMIT 1;

  IF key_name IS NULL THEN
    RAISE EXCEPTION 'No active encryption key found';
  END IF;

  -- VAULT INTEGRATION NOTE:
  -- Production implementation should use Supabase Vault:
  --   SELECT decrypted_secret INTO key_value
  --   FROM vault.decrypted_secrets
  --   WHERE name = key_name;
  --
  -- For initial implementation, we use app setting as fallback.
  -- This is acceptable for MVP but should be upgraded to Vault
  -- before handling production user data.
  SELECT current_setting('app.encryption_key', true) INTO key_value;

  IF key_value IS NULL THEN
    RAISE EXCEPTION 'Encryption key not configured';
  END IF;

  RETURN key_value;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Encryption Functions

```sql
-- 4. Create encryption function
CREATE OR REPLACE FUNCTION encrypt_sensitive(plaintext TEXT)
RETURNS BYTEA AS $$
DECLARE
  key TEXT;
BEGIN
  key := get_active_encryption_key();
  RETURN pgp_sym_encrypt(plaintext, key);
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- 5. Create decryption function
CREATE OR REPLACE FUNCTION decrypt_sensitive(ciphertext BYTEA)
RETURNS TEXT AS $$
DECLARE
  key TEXT;
BEGIN
  key := get_active_encryption_key();
  RETURN pgp_sym_decrypt(ciphertext, key);
EXCEPTION WHEN OTHERS THEN
  -- Log error but don't expose details
  RAISE WARNING 'Decryption failed for record';
  RETURN NULL;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Schema Modifications for Prompts

```sql
-- 6. Add encrypted columns to prompts
ALTER TABLE prompts ADD COLUMN text_encrypted BYTEA;
ALTER TABLE prompts ADD COLUMN encryption_key_version INTEGER DEFAULT 1;

-- 7. Create encryption trigger for prompts
CREATE OR REPLACE FUNCTION encrypt_prompt_text()
RETURNS TRIGGER AS $$
BEGIN
  IF NEW.text IS NOT NULL THEN
    NEW.text_encrypted := encrypt_sensitive(NEW.text);
    NEW.encryption_key_version := (
      SELECT key_version FROM encryption_keys WHERE status = 'active' LIMIT 1
    );
    -- Optionally clear plaintext after encryption
    -- NEW.text := NULL;  -- Enable after migration complete
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER prompts_encrypt_trigger
  BEFORE INSERT OR UPDATE ON prompts
  FOR EACH ROW EXECUTE FUNCTION encrypt_prompt_text();

-- 8. Create decryption view for prompts
CREATE OR REPLACE VIEW prompts_decrypted AS
SELECT
  id,
  user_id,
  project_id,
  team_id,
  CASE
    WHEN text_encrypted IS NOT NULL THEN decrypt_sensitive(text_encrypted)
    ELSE text
  END AS text,
  char_count,
  word_count,
  source,
  context,
  analysis,
  scores,
  classifications,
  metadata,
  created_at,
  updated_at
FROM prompts;
```

### Key Rotation Functions

```sql
-- 9. Key rotation function
CREATE OR REPLACE FUNCTION rotate_encryption_key(new_vault_secret_name TEXT)
RETURNS INTEGER AS $$
DECLARE
  new_version INTEGER;
BEGIN
  -- Mark current active key as rotating
  UPDATE encryption_keys
  SET status = 'rotating', rotated_at = NOW()
  WHERE status = 'active';

  -- Get next version number
  SELECT COALESCE(MAX(key_version), 0) + 1 INTO new_version
  FROM encryption_keys;

  -- Insert new key
  INSERT INTO encryption_keys (key_version, vault_secret_name, status)
  VALUES (new_version, new_vault_secret_name, 'active');

  RETURN new_version;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- 10. Batch re-encryption function
CREATE OR REPLACE FUNCTION reencrypt_prompts_batch(batch_size INTEGER DEFAULT 1000)
RETURNS INTEGER AS $$
DECLARE
  records_processed INTEGER := 0;
  target_version INTEGER;
  old_key TEXT;
  new_key TEXT;
  rec RECORD;
BEGIN
  -- Get current active key version
  SELECT key_version INTO target_version
  FROM encryption_keys WHERE status = 'active' LIMIT 1;

  -- Get old key for decryption (assume version - 1)
  -- In production, lookup by the record's encryption_key_version

  -- Process batch
  FOR rec IN
    SELECT id, text_encrypted, encryption_key_version
    FROM prompts
    WHERE encryption_key_version < target_version
    LIMIT batch_size
    FOR UPDATE SKIP LOCKED
  LOOP
    -- Decrypt with old key, re-encrypt with new key
    UPDATE prompts
    SET
      text_encrypted = encrypt_sensitive(decrypt_sensitive(rec.text_encrypted)),
      encryption_key_version = target_version,
      updated_at = NOW()
    WHERE id = rec.id;

    records_processed := records_processed + 1;
  END LOOP;

  RETURN records_processed;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
```

### Application Integration

```typescript
// lib/db/prompts.ts

import { createServerClient } from '@/lib/supabase/server';

export async function getPrompt(id: string) {
  const supabase = await createServerClient();

  // Use decrypted view
  const { data, error } = await supabase
    .from('prompts_decrypted')
    .select('*')
    .eq('id', id)
    .single();

  if (error) throw error;
  return data;
}

export async function capturePrompt(prompt: CaptureInput) {
  const supabase = await createServerClient();

  // Insert triggers encryption automatically
  const { data, error } = await supabase
    .from('prompts')
    .insert({
      text: prompt.text,  // Will be encrypted by trigger
      user_id: prompt.userId,
      project_id: prompt.projectId,
      team_id: prompt.teamId,
      // ... other fields
    })
    .select('id')
    .single();

  if (error) throw error;
  return data;
}
```

### Migration Strategy

1. **Phase 1**: Add encrypted columns alongside existing columns
2. **Phase 2**: Backfill encrypted data from existing plaintext
3. **Phase 3**: Update application to read from decrypted view
4. **Phase 4**: Stop writing plaintext (clear after encryption)
5. **Phase 5**: Drop plaintext columns after verification

### Security Considerations

| Risk | Mitigation |
|------|------------|
| Key in database | Store in Vault, pass via session variable |
| Key in logs | SECURITY DEFINER prevents logging key value |
| Decrypt all data | RLS still applies to decrypted view |
| Key loss | Backup key in secure external location |
| Performance | Encryption adds ~5-10% overhead (must stay <50ms per operation) |

### Future Considerations

**Per-Team Encryption Keys:** The PRD mentions per-team keys as a future enhancement. This implementation uses a single system-wide encryption key. The schema is designed to support per-team keys in the future by:
- The `encryption_keys` table can be extended with a `team_id` column
- The `get_active_encryption_key()` function can accept a team_id parameter
- Key rotation functions can operate per-team

This enhancement is **out of scope** for the initial implementation but the architecture supports it.
